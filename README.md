## Folder Structure and Function

The project is organized into the following main directories:

*   **`.github/workflows/`**: Contains CI/CD (Continuous Integration/Continuous Deployment) pipeline configurations using GitHub Actions.
    *   `docker-publish.yml`: Defines a workflow for building and publishing the application's Docker image, likely for production environments.
    *   `docker-publish_qa.yml`: Defines a similar workflow, but targeted for QA (Quality Assurance) or testing environments.
*   **`conections/`**: Manages database connections.
    *   `mongo.py`: Handles the connection to a MongoDB database, using environment variables for configuration. It provides a utility function to establish and return a database client.
*   **`services/`**: Contains the core business logic of the application.
    *   `functions.py`: Implements specific operations and functionalities, such as user comment management. It interacts with the data access layer and includes validation logic.
*   **`tests/`**: Houses automated tests for the application.
    *   `route_test.py`: An integration test script for testing API endpoints by making live HTTP requests.
    *   `test_delete_comment.py`: Likely contains more specific unit or integration tests for the comment deletion functionality.
*   **`__pycache__/`**: Stores Python bytecode cache files (`.pyc`), automatically generated by the Python interpreter to speed up module loading. This directory is typically ignored by version control.

Key files in the root directory:

*   `main.py`: The main entry point for the Flask web application. It handles incoming HTTP requests, routing, authentication, and delegates tasks to the service layer.
*   `dockerfile`: Contains instructions to build a Docker image for the application, enabling containerized deployment.
*   `requirements.txt`: Lists all Python package dependencies required by the project.
*   `.gitignore`: Specifies files and directories that Git should ignore during version control.

## Backend Design Pattern

The backend follows a **Layered Architecture** pattern. This pattern separates the application into distinct layers, each with a specific responsibility:

1.  **Presentation Layer (`main.py`)**: Responsible for handling HTTP requests and responses, API routing, and initial request validation (like JWT authentication).
2.  **Service Layer (`services/functions.py`)**: Contains the core business logic of the application. It orchestrates operations, implements business rules, and coordinates between the presentation and data access layers.
3.  **Data Access Layer (`conections/mongo.py`)**: Manages all communication with the database (MongoDB in this case). It handles data retrieval, storage, and updates.

This separation of concerns promotes modularity, maintainability, and testability.

## Communication Architecture

*   **External Communication (Client-to-Server):**
    The application exposes a **REST API** for clients to interact with.
    *   **Protocol:** HTTP/S
    *   **Data Format:** JSON for request bodies and responses.
    *   **Authentication:** JSON Web Tokens (JWT) are used for securing endpoints. Clients must send a JWT in the `Authorization: Bearer <token>` header.

*   **Internal Communication (Between Layers):**
    Communication between the different layers within the application (Presentation, Service, Data Access) is achieved through **direct Python function calls**. For example, `main.py` calls functions in `services/functions.py`, which in turn call functions in `conections/mongo.py`.

## Folder Pattern

The project utilizes a **Layer-Based Folder Pattern**. Directories like `conections/` and `services/` directly correspond to the architectural layers (Data Access Layer, Service Layer), grouping modules by their technical role rather than by application feature.

## Endpoint Instructions

### PUT /delete-comment

*   **Purpose:** Logically deletes a comment by setting its "Status" field to `0`. This action is restricted to the user who originally created the comment.
*   **HTTP Method:** `PUT`
*   **URL:** `/delete-comment`
*   **Headers:**
    *   `Authorization`: `Bearer <JWT_TOKEN>` (Required. The JWT token for authenticating the user.)
    *   `Content-Type`: `application/json` (Required if sending a JSON body.)
*   **Request Body (JSON):**
    ```json
    {
        "comment_id": "string"
    }
    ```
    *   `comment_id` (string, required): The unique identifier of the comment to be deleted.

*   **Responses:**
    *   **`200 OK`**: Comment successfully marked as deleted.
        ```json
        {
            "message": "Comment deleted successfully"
        }
        ```
    *   **`400 Bad Request`**: Invalid `comment_id` format.
        ```json
        {
            "error": "Invalid comment ID format"
        }
        ```
    *   **`401 Unauthorized`**:
        *   Token is missing, malformed, or invalid.
            ```json
            {
                "error": "Token missing or invalid" 
            }
            ```
            ```json
            {
                "error": "Invalid token"
            }
            ```
        *   Token has expired.
            ```json
            {
                "error": "Token expired"
            }
            ```
    *   **`403 Forbidden`**: The authenticated user is not authorized to delete this comment (i.e., not the owner).
        ```json
        {
            "error": "Unauthorized to delete this comment"
        }
        ```
    *   **`404 Not Found`**: The specified comment was not found.
        ```json
        {
            "error": "Comment not found"
        }
        ```
    *   **`500 Internal Server Error`**: An unexpected error occurred on the server while attempting to delete the comment.
        ```json
        {
            "error": "Failed to delete comment: <specific_error_details>"
        }
        ```
